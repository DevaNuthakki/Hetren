# P09.4 K5D-4D2F — Authorization and Canonical Identity Design

**Status:** PROPOSED ENGINEERING CONTRACT — NOT APPROVED FOR
PROTECTED IMPLEMENTATION OR SCIENTIFIC EXECUTION

**Checkpoint:** `150195417edb58546438852e8f147d89854e6fc9`

**Frozen scientific authority:**
`docs/portfolio/p09.4-protected-study-preregistration.md`

**Engineering references:**
- K5D-3 development persistence contract.
- K5D-4C protected-readiness gap matrix.
- K5D-4D2 architecture options and observed platform evidence.

This document proposes D1 authorization and D2 canonical-identity
controls for Option B. It neither changes the frozen scientific
protocol nor authorizes a real protected C1 seed.

## 1. Decision scope

The objective is to design a controller that can:

1. Reject unauthorized requests before an irreversible claim.
2. Bind a request to one designated scientific identity.
3. Prevent accidental rerolls within a defined trusted boundary.
4. Keep private C1 material separate from public evidence.
5. Preserve auditable failure and incomplete states.

This proposal does not establish independent governance,
cross-machine uniqueness, crash durability, or production
authorization.

Option B remains a conditional development candidate.

## 2. D1 — Authorization contract

### 2.1 Distinct responsibilities

The proposed design separates:

- Approval issuance: deciding whether a specific irreversible
  protected operation is permitted.
- Approval verification: checking authenticity, scope,
  binding, validity, and replay restrictions.
- Execution: consuming the one-shot identity and performing
  only the operation explicitly authorized.

Separating these responsibilities in code does not prove
independent human or organizational control.

An approval document created and verified by the same
unrestricted operator cannot be called independently issued
authorization.

No qualifying approval issuer or trust anchor currently exists.

### 2.2 Proposed approval bindings

A future reviewable approval record should bind:

- an explicitly versioned approval schema;
- a unique approval identifier;
- issuing authority identity;
- specifically authorized operation;
- the frozen study version and protocol digest;
- the approved source or executable lineage;
- the canonical protected C1 identity;
- the canonical target-root identity;
- approved artifact schema version;
- defined validity and single-use semantics;
- authenticated approval evidence.

The intended operation is:

`CREATE_PROTECTED_C1_SEED`

The operation identifier is a proposed engineering constant,
not permission to invoke any seed-generation function.

Cryptographic authentication, if chosen, must have a genuine
trust anchor protected from unauthorized executors.

No real signing key, signing service, approval token, or
authorization record is created by this document.

### 2.3 Fail-closed verification ordering

Proposed order:

1. Resolve and validate the fixed engineering configuration.
2. Verify frozen protocol and source lineage.
3. Verify the designated canonical identity and root binding.
4. Obtain the approval evidence without invoking randomness.
5. Validate its authenticity, validity, operation, identity,
   lineage, and root binding.
6. Reject missing, invalid, ambiguous, expired, replayed, or
   incorrectly scoped approval before identity claim.
7. Only after all preflight gates pass may a separately
   authorized operation claim its one-shot identity.
8. Persist a STARTED record before any real randomness call.

An error in steps 1-6 must not create an identity or call
the seed factory.

A failure after irreversible claim must never trigger
automatic regeneration of the same identity.

The durability requirements for steps 7-8 remain subject
to a separate engineering review.

### 2.4 Current single-developer limitation

For Hetren's portfolio workflow, synthetic approval fixtures
may demonstrate correct verification and rejection logic.

They are not proof of external review, independent issuer
control, or production authorization.

If an independently trusted approval mechanism is required
but unavailable, the protected execution gate stays closed.

No developer test, local configuration, or document can
silently substitute for the missing authority.

## 3. D2 — Canonical protected identity

### 3.1 Proposed identity inputs

A future canonical identity should be derived from an
unambiguous, versioned combination of:

- frozen protected-study identifier;
- study version;
- frozen protocol digest;
- C1 seed purpose identifier;
- approved evidence schema version.

The C1 purpose identifier is:

`c1_seed_v1`

This is a proposed identity schema, not an approved filesystem
path or claim that the identifier has been consumed.

The canonical representation must define encoding,
field ordering, allowed values, and validation.

A digest of those fields can bind records to an identity.
A digest does not enforce global uniqueness by itself.

### 3.2 Trusted root and identity ownership

The future protected operation should use one explicitly
approved root controlled by the authorized environment.

A caller must not supply an arbitrary replacement root.

A caller must not select another directory to rerun the
same scientific identity after a failed claim.

The root binding should be verified against the approval
record before the irreversible operation.

No real protected root is selected or created here.

The observed repository artifact namespace is currently
absent and has not been approved for protected storage.

A root outside the repository is a design preference,
not a frozen protocol requirement or an approved decision.

### 3.3 Filesystem name and path constraints

For Option B, proposed controlled relative components must:

- be explicitly defined by the approved schema;
- reject empty components, `.`, and `..`;
- reject absolute paths and caller-defined parent traversal;
- avoid traversal through symbolic links;
- be opened relative to trusted directory descriptors;
- be verified against the intended file/directory type;
- fail closed when required platform primitives are absent.

The macOS synthetic probe observed that an intermediate
symbolic link was followed despite final-component
`O_NOFOLLOW`.

The same probe observed that `..` relative to a directory
descriptor reached its parent directory.

Accordingly, using `dir_fd` or `O_NOFOLLOW` in isolation
must not be described as full path confinement.

Actual race and crash behavior remain unqualified.

### 3.4 Scope of uniqueness

An exclusive claim under one trusted root can support
one-shot behavior inside that particular authority boundary.

It does not prevent an unrestricted operator from cloning
a repository, creating another root, or running on a different
machine.

Global cross-host uniqueness requires a common coordinating
authority or stronger environmental constraints.

That mechanism has not been selected.

The development controller must not make claims beyond
the declared local identity boundary.

## 4. Proposed operation lifecycle

This is a design model, not implemented protected behavior.

PREFLIGHT
-> AUTHORIZATION_VERIFIED
-> IDENTITY_CLAIMED
-> STARTED_DURABLY_RECORDED
-> SEED_GENERATED
-> PRIVATE_EVIDENCE_PERSISTED
-> PUBLIC_COMMITMENT_PERSISTED
-> SUCCEEDED

Failure rules:

- Before IDENTITY_CLAIMED, rejection does not consume identity.
- After IDENTITY_CLAIMED, failure consumes the identity.
- A FAILED disposition should be recorded where safely possible.
- An incomplete claimed identity remains consumed.
- File visibility must not be confused with confirmed durability.
- Missing disposition after a crash must not enable reroll.
- No recovery path may call the seed factory again for the same
  claimed identity.

The lifecycle requires later review of ordering, failure
atomicity, access control, target filesystem guarantees, and
recovery evidence before implementation approval.

## 5. Public and private evidence boundaries

The public record should expose only approved nonsecret data,
including a seed commitment and required lineage references.

The raw C1 seed belongs exclusively to the authorized private
treatment-execution evidence boundary.

Proposed schemas must distinguish:

- approval evidence;
- one-shot claim and lifecycle disposition;
- private C1 seed bytes;
- public cryptographic commitment;
- lineage and verification evidence.

Public logging, exception formatting, and diagnostic output
must never include raw protected seed bytes.

No production evidence schema is approved by this document.

## 6. Development-only acceptance criteria

Future synthetic tests should demonstrate:

- Missing approval rejects before identity claim.
- Invalid authentication rejects before identity claim.
- Wrong operation rejects before identity claim.
- Wrong protocol digest rejects before identity claim.
- Wrong study/version rejects before identity claim.
- Wrong root binding rejects before identity claim.
- Expired or replayed approval rejects before claim.
- Arbitrary alternate-root requests are rejected.
- Dot, parent, absolute, and symlink traversal are rejected.
- Competing claims cannot both succeed in one trusted root.
- A claimed failure never invokes seed generation twice.
- Private synthetic fixture bytes stay out of public records.
- Unsupported filesystem operations fail closed.
- Incomplete states are not silently reclassified as success.

All such tests must use synthetic fixtures only.

These criteria describe intended behavior, not verified
implementation results.

## 7. Open design decisions

The following are unresolved and require separate review:

**A1 — Authorization issuer and verifier:**
Who genuinely controls approval, and how is its authenticity
independently verifiable?

**A2 — Trust anchor:**
How is the approval-verification authority separated from
an unauthorized executor?

**I1 — Canonical root:**
Which exact environment and location may own the identity?

**I2 — Identity serialization:**
What versioned encoding and lineage form become authoritative?

**I3 — Evidence schema:**
What approved public/private paths, permissions, and fields
will be used?

**I4 — Durability and recovery:**
What happens after a claim when storage durability or process
completion cannot be established?

**I5 — Cross-host threat model:**
Is a strictly local trusted-user boundary sufficient, or is
external coordination required?

These decisions cannot be inferred from Python API availability.

## 8. Recommendation and authority status

**Conditional engineering recommendation:**
Retain Option B for narrowly scoped, synthetic-only development
once authorization and identity validation contracts are reviewed.

**Not yet approved:**
- independent authorization semantics;
- canonical protected root;
- production identity/evidence schema;
- protected OS-random capability;
- crash recovery guarantees;
- real protected C1 seed execution.

The next review must examine A1, A2, I1-I5 and determine
whether a defensible local trust model is achievable without
creating a general-purpose secret-management system.

**PROTECTED K5D AUTHORIZATION REMAINS CLOSED.**

The frozen protected-study preregistration remains authoritative.

## 9. K5D-4D2H Synthetic Acceptance Contract

**Status: PROPOSED DEVELOPMENT-ONLY CONTRACT —
NOT IMPLEMENTED AND NOT SCIENTIFIC AUTHORIZATION**

This addendum defines testable acceptance behavior for a future
synthetic-only authorization and identity validation increment.

It does not approve independent authorization, protected storage,
production seed generation, or any later scientific phase.

### 9.1 Restricted development boundary

The future development harness must:

- use a disposable test-owned root outside the repository;
- reject roots inside the Hetren repository;
- use an explicitly synthetic identity;
- use fixed nonsecret synthetic seed fixtures;
- never create the real `protected_v1` or `c1_seed_v1` identities;
- never create real signing keys or approval credentials;
- never provide a protected seed-generation CLI;
- never use OS randomness to generate a scientific study seed.

The test harness controls the synthetic root, test verifier,
fixed clock, and synthetic seed factory.

The operation request must not control those capabilities.

### 9.2 Exact synthetic identity

The proposed identity contains exactly five string fields:

- `schema`: `hetren.dev.c1-authorization-identity.v1`
- `study_id`: `P09.4`
- `study_version`: `synthetic_only`
- `purpose`: `synthetic_c1_authorization`
- `protocol_sha256`: the frozen protocol digest

Frozen protocol SHA256:

`46ea27e825bedbfbd8ee0443173884f904f20881fc929a4c44fae30c550e7621`

Canonical serialization is defined as the UTF-8 output of
`json.dumps(identity, sort_keys=True, separators=(",", ":"), ensure_ascii=True, allow_nan=False).encode("utf-8")`.

The serialized bytes contain no BOM or trailing newline.

The identity digest is lowercase hexadecimal SHA-256 of
those canonical bytes.

Unexpected fields, missing fields, wrong types, wrong values,
malformed hashes, and ambiguous encodings must fail validation.

This synthetic identity is not an approved protected identity.

Its digest does not prove authorization or global uniqueness.

### 9.3 Synthetic root binding

The trusted test harness supplies one root-binding identifier
for its disposable synthetic filesystem fixture.

The request may not specify:

- another filesystem root;
- an arbitrary output directory;
- a private seed path;
- a production artifact namespace;
- an alternate seed factory;
- or a production execution mode.

The injected verifier must check that the request, identity,
approval fixture, and root-binding identifier agree.

The root binding is a development test mechanism.
It is not independent proof of secure root ownership.

### 9.4 Synthetic operation and approval

The only permitted operation identifier is:

`SIMULATE_C1_AUTHORIZED_CLAIM`

No real protected operation identifier is accepted.

The proposed request fields are:

- `operation`
- `identity_sha256`
- `approval_fixture_ref`
- `root_binding_id`

The harness-controlled verifier validates:

- operation binding;
- canonical identity binding;
- frozen protocol digest binding;
- synthetic root binding;
- allow/deny decision;
- simulated issuance and expiration;
- simulated replay status.

Time-dependent behavior uses an injected fixed clock.

A caller-supplied Boolean indicating approval must never be
treated as valid authorization.

Synthetic approval fixtures do not constitute independently
issued scientific authorization.

### 9.5 Required validation ordering

The proposed flow is:

1. Validate the synthetic execution boundary.
2. Validate environment capabilities and the fixed test root.
3. Validate request shape, fields, and types.
4. Validate canonical identity serialization and digest.
5. Validate the frozen protocol binding.
6. Execute the injected test-only approval verifier.
7. Reject invalid, missing, denied, expired, replayed,
   or incorrectly scoped synthetic approval.
8. Reject already claimed or incomplete identities.
9. Exclusively claim the synthetic identity.
10. Persist STARTED before invoking the synthetic factory.
11. Invoke the synthetic factory at most once.
12. Persist private synthetic data and public commitment.
13. Record terminal success or handled failure.

Steps 1 through 8 must not consume an unclaimed identity.

They must not call the synthetic seed factory.

After step 9, the identity is consumed even if later work fails.

If STARTED persistence fails after claim, the identity remains
consumed and incomplete.

Failure must never enable regeneration using that identity.

These rules are proposed for future implementation.

## 10. K5D-4D2J Synthetic Interface Decisions

**Status: DEVELOPMENT DESIGN DECISIONS ONLY**

The following decisions resolve Q1-Q6 for a limited
synthetic-only implementation increment.

They do not approve protected scientific execution, independent
authorization, or a production storage boundary.

### 10.1 Q1 — Deterministic validation precedence

The first failing stage in the following ordered preflight
pipeline determines the public rejection category:

1. Synthetic runtime and platform prerequisites:
   DEV_UNSUPPORTED_ENV.
2. Exact request schema and field types:
   DEV_INVALID_REQUEST.
3. Trusted frozen-protocol source and digest:
   DEV_PROTOCOL_MISMATCH.
4. Fixed synthetic identity and digest:
   DEV_IDENTITY_MISMATCH.
5. Harness-owned root and root-binding agreement:
   DEV_ROOT_MISMATCH.
6. Missing approval fixture:
   DEV_APPROVAL_MISSING.
7. Harness-controlled approval verification.
8. Prior identity disposition and claim status.

Within stage 7, the verifier applies this precedence:

1. Wrong operation, identity, protocol or root scope:
   DEV_APPROVAL_SCOPE.
2. Outside the synthetic validity interval:
   DEV_APPROVAL_EXPIRED.
3. Simulated approval reuse:
   DEV_APPROVAL_REPLAY.
4. Explicit rejection:
   DEV_APPROVAL_DENIED.
5. Otherwise, ACCEPT.

A missing fixture never reaches the verifier.

A verifier exception, invalid verifier result, or unexpected
pre-claim implementation error maps to DEV_INTERNAL_FAILURE
and must leave the identity unclaimed.

Missing, extra, or wrongly typed request fields are classified
before comparing request values.

A malformed digest representation is DEV_INVALID_REQUEST.
A correctly formatted but incorrect digest is
DEV_IDENTITY_MISMATCH.

All field-shape checks must reject Boolean values where
strings or integers are expected.

The trusted protocol mismatch test must inject a synthetic
protocol-provider failure; it must not edit the frozen protocol.

When multiple defects exist, tests verify that the first
applicable stage wins.

These are fixed development-interface decisions, not changes
to the frozen protected-study protocol.

### 10.2 Q2 — Injected verifier interface

The verifier belongs to the trusted development test harness.

Proposed conceptual interface:

verify(
    fixture_reference,
    operation,
    identity_sha256,
    protocol_sha256,
    root_binding_id,
    fixed_now_utc,
) -> ApprovalDecision

ApprovalDecision is a structured, immutable test outcome
containing one of:

- ACCEPT
- DENIED
- SCOPE
- EXPIRED
- REPLAY

The public DEV_APPROVAL_MISSING category is assigned before
calling the verifier.

Fixture references are identifiers in a harness-controlled
allowlist, not arbitrary filesystem paths or network URLs.

The verifier reads only synthetic fixtures from the harness.

The untrusted operation request cannot replace the verifier,
its fixture registry, its clock, or the synthetic seed factory.

Unexpected exceptions fail closed as DEV_INTERNAL_FAILURE
before claim.

The verifier cannot write the claim or invoke the seed factory.

This adapter proves simulated verification mechanics only.
It does not establish a real trusted approval issuer.

### 10.3 Q3 — Synthetic root binding

For development, the fixture root is created and owned
by the test harness outside the Hetren repository.

The proposed fixed logical binding label is:

hetren-dev-fixture-root-v1

This label is meaningful only inside one trusted fixture
context. It is not globally unique or an authorization token.

The harness retains an already-open directory descriptor
and verifies its filesystem identity when accessing the
fixture root.

A request cannot provide a new root directory or override
the harness-owned descriptor.

The root label and file-descriptor identity have different
roles:

- the label binds the synthetic approval to its fixture;
- the descriptor anchors operations to the opened directory.

Neither proves protection against a malicious same-user
process or cross-host duplicate identity.

If the expected trusted root cannot be established,
reject before claim.

If root integrity becomes uncertain after claim,
preserve consumed identity and fail closed.

### 10.4 Q4 — Path-test separation

AT-10 is divided into two test groups.

AT-10A: External request schema.

A caller who supplies an extra root, path, parent-directory,
seed-factory, or output-directory field receives
DEV_INVALID_REQUEST before claim.

AT-10B: Internal filesystem boundary.

Harness-controlled negative fixtures test absolute paths,
empty components, dot components, parent traversal, and
symbolic links.

Failures before claim return DEV_ROOT_MISMATCH or
DEV_UNSUPPORTED_ENV according to the failing preflight
condition.

Failures after claim must never release the claimed identity.

No test uses real protected identifiers or artifact directories.

The test suite must verify that no path escape writes occur.

### 10.5 Q5 — Claim-state and recovery outcomes

The proposed one-shot state distinctions are:

UNCLAIMED:
No identity claim exists. Successful preflight may proceed.

CLAIMED_INCOMPLETE:
The identity was claimed but terminal success is not
reliably established. It is permanently unavailable
for regeneration.

SUCCEEDED:
The identity was consumed with a successful terminal record.

FAILED:
The identity was consumed with a recorded failed attempt.

Before claim:

- rejection does not consume identity;
- synthetic factory invocation count remains zero;
- an unexpected exception returns DEV_INTERNAL_FAILURE.

After claim:

- known persistence failures return DEV_PERSISTENCE_FAILED;
- unexpected failures return DEV_INTERNAL_FAILURE;
- the error outcome must explicitly retain the fact that
  the identity has been consumed;
- no exception handler may reset the claim or retry the factory.

A previously SUCCEEDED identity returns DEV_ALREADY_CLAIMED.

A previously FAILED or CLAIMED_INCOMPLETE identity returns
DEV_CLAIM_INCOMPLETE.

If a competing exclusive claim is lost, inspect the available
trusted disposition and classify conservatively.
Never create a second claim to resolve ambiguity.

No claimed identity may be regenerated after an incomplete
STARTED record, process interruption, or uncertain durability.

Tests must distinguish public error reporting from durable
filesystem evidence. An exception result alone does not
prove that a disposition was persisted.

Real crash and power-loss guarantees remain unqualified.

### 10.6 Q6 — Canonical identity vectors

The positive development identity has exactly five string
fields, as defined in Section 9.2.

Canonical encoding uses UTF-8 JSON with:

- sorted keys;
- compact separators;
- ASCII escaping;
- NaN and infinity disallowed;
- no BOM;
- no trailing newline.

The verified positive vector has:

Canonical byte length: 228

SHA-256:
1e99155aaae81f740868692327d86db2be030653d9ddb53800de0a978f148c68

The test suite must independently reconstruct and compare
the exact canonical bytes and expected digest.

Required negative vectors:

VECTOR-01: Remove a required identity field.
Expected: reject identity validation.

VECTOR-02: Add an unexpected identity field.
Expected: reject identity validation.

VECTOR-03: Replace a required string with an integer.
Expected: reject identity validation.

VECTOR-04: Replace a required string with a Boolean.
Expected: reject identity validation.

VECTOR-05: Supply malformed request identity SHA-256.
Expected: DEV_INVALID_REQUEST.

VECTOR-06: Supply a different valid-length identity SHA-256.
Expected: DEV_IDENTITY_MISMATCH.

VECTOR-07: Inject a wrong digest through the trusted
synthetic protocol provider.
Expected: DEV_PROTOCOL_MISMATCH.

VECTOR-08: Provide an approval scoped to another
protocol digest.
Expected: DEV_APPROVAL_SCOPE.

VECTOR-09: Add a BOM or trailing newline to supplied
canonical identity bytes.
Expected: reject byte-for-byte canonical comparison.

VECTOR-10: Reorder source dictionary insertion order.
Expected: identical canonical bytes and digest.

The implementation must distinguish malformed supplied
identity bytes from a properly formed but incorrect identity.

Canonical serialization does not provide cryptographic
authenticity, independent approval, or one-shot uniqueness.
