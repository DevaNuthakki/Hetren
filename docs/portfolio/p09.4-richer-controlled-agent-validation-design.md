# P09.4 Richer Controlled Multi-Step Agent Validation Design

## Status

**PRE-PREREGISTRATION ARCHITECTURE DESIGN — NO PROTECTED EXECUTION AUTHORITY**

This document freezes the architectural direction for P09.4.

It does not freeze the final protected population, exact numerical budgets,
decision thresholds, randomization schedule, or protected execution package.

Those values must be calibrated using development-only evidence and then
preregistered before any protected P09.4 result exists.

---

## Relationship to P09.3

P09.3 established bounded evidence for H1 in a deterministic controlled
mechanism experiment.

P09.4 must not repeat that compact synthetic construction merely to reproduce
another favorable result.

P09.4 asks whether the active-diagnosis mechanism remains useful when the
controlled environment becomes substantially more agent-like:

- longer execution trajectories;
- persistent state;
- multiple tool or environment interactions;
- heterogeneous failure mechanisms;
- interventions whose evidence emerges from workflow execution;
- and greater ambiguity among plausible explanations.

P09.3 remains immutable prior evidence.

---

## Scientific scope

P09.4 remains a stronger validation of H1.

It does not attempt to establish H2, H3, H4, or H5.

The primary scientific object remains diagnosis policy.

Repair generation, Repair Contrast, independent verification, candidate
eligibility, authorization, and deployment are outside the primary P09.4
success criterion.

Existing repair and verification contracts may be reused later, but they must
not be allowed to confound the H1 comparison.

---

## Selected environment direction

P09.4 will use a richer deterministic incident-response / tool-agent
environment built on the existing Python foundation.

The existing incident-triage and deterministic-tool-agent implementations are
the preferred reuse targets because they already contain meaningful state,
tool-call/tool-result behavior, traces, and workflow semantics.

P09.4 should extend those ideas into a dedicated experimental environment
rather than mutating P09.3 or silently repurposing its protected artifacts.

A browser framework, Kubernetes environment, external orchestration system,
database, queue, or new agent framework is not required for this validation
layer.

If later design evidence shows that a meaningful new technology is necessary,
it must be reviewed before introduction.

---

## Candidate workflow model

Each case should represent an agent attempting a multi-stage operational
incident workflow.

A candidate workflow may contain stages such as:

1. receive or load incident context;
2. retrieve service or account metadata;
3. select an appropriate tool or data source;
4. construct tool parameters;
5. execute one or more tool interactions;
6. normalize or transform returned data;
7. combine results with persistent workflow state;
8. apply incident policy or decision logic;
9. validate the resulting evidence;
10. produce the final diagnosis-relevant workflow outcome.

The exact stage count is not frozen by this design document.

Development work must determine a credible minimum trajectory complexity, and
that requirement must be frozen before protected evaluation.

---

## Persistent state

The richer environment must contain state that matters to later behavior.

Candidate state includes:

- incident metadata;
- selected service or tool identity;
- transformed request parameters;
- cached or previously observed values;
- intermediate tool results;
- normalized records;
- policy context;
- stage completion state;
- and final workflow evidence.

State transitions must be observable through ordinary treatment-visible
evidence without revealing evaluator-only latent fault labels.

---

## Primary controlled fault families

The primary known-fault population should draw from the existing registered
fault taxonomy:

### F1 — Tool-selection fault

The workflow selects a wrong but plausible tool, endpoint, or implementation.

### F2 — Parameter-transformation fault

The intended tool is correct but one or more inputs are transformed, omitted,
or substituted incorrectly.

### F3 — Sequencing or orchestration fault

Individually valid actions are executed in an incorrect order or control-flow
path.

### F4 — State or context fault

The workflow consumes stale, incomplete, corrupted, or inappropriate state.

### F5 — Tool or environment interaction fault

The intended action encounters tool or environment response semantics that
invalidate the workflow's assumption.

P09.4 should remain single-latent-fault in its primary controlled population.

Multiple simultaneous faults are intentionally deferred so that P09.4 changes
one major scientific difficulty dimension at a time.

F6 validation/oracle weakness is not a primary H1 target in this phase because
it directly concerns the quality of validation rather than only diagnosis
policy. It may be used as a separately registered negative control or tested
in later Repair Contrast / verification work.

---

## Rival explanations

A case must not disclose its latent fault family to treatment.

Treatment receives a diagnosis problem containing multiple plausible
hypotheses that are consistent with the initially observable failure.

A target design goal is at least three plausible rival explanations for every
known-fault protected case.

The exact hypothesis cardinality distribution must be frozen before protected
evaluation.

Cases should avoid trivial one-observation diagnosis whenever technically
possible.

---

## Diagnostic interventions

P09.4 interventions must obtain evidence by executing workflow behavior.

They must not return a verdict by directly reading the hidden fault label.

Candidate intervention classes include:

### Tool-choice probe

Replay or sandbox the relevant workflow stage using an alternative or
canonical tool selection and compare observable behavior.

### Parameter probe

Run a dry-run, echo, validation, or canonical-parameter execution that tests
whether the suspected transformation is responsible for the failure.

### Sequencing probe

Replay a suspect stage with the expected prerequisite state or alternate
ordering and observe whether the failure behavior changes.

### State-refresh probe

Reconstruct or refresh the relevant context/state in an isolated execution and
compare the resulting workflow evidence.

### Environment-contract probe

Exercise a tool/environment contract to distinguish environment response
semantics from agent-side selection or transformation faults.

The final experiment catalogue must be frozen before protected evaluation.

---

## Intervention isolation

Diagnostic experiments must not accidentally repair or permanently contaminate
the shared case before later experiments run.

The preferred design is to execute each diagnostic intervention against an
isolated clone or reproducible snapshot of the same failure state.

Within an arm, the planner may accumulate observations across experiments, but
the underlying diagnostic experiment must begin from the frozen case state
unless the preregistered experiment explicitly tests state evolution.

This separation prevents experiment ordering from becoming an uncontrolled
source of state contamination.

---

## Treatment arms

P09.4 should preserve the same conceptual comparison family used in P09.3:

- C0 — trace-only diagnosis;
- C1 — seeded-random active experiment selection;
- C2 — maximum raw expected information gain;
- C3 — HEAL information gain per declared cost.

The richer environment may require implementation changes around experiment
execution, but those changes must not silently change the conceptual meaning
of the comparison arms.

Every arm begins with the same initial observable case information.

---

## Observable-information parity

Before active intervention begins, comparison arms must receive the same:

- initial failure trace;
- initial workflow state visible to treatment;
- hypothesis set;
- experiment catalogue;
- ordinary tool definitions;
- and diagnosis budget definition.

C3 must not receive evaluator-only fault metadata.

C0, C1, and C2 must not be deprived of ordinary evidence solely to create an
advantage for C3.

Evidence obtained by an actively selected experiment may naturally differ
between arms because acquiring that evidence is the treatment being tested.

---

## Hidden truth boundary

Evaluator-only truth may include:

- latent fault family;
- exact injected fault site;
- exact fault parameters;
- expected correct diagnosis;
- protected assignment metadata;
- and any evaluator-only negative-control identity.

The planner, diagnosis policy, treatment arm, and ordinary treatment-visible
workflow state must not consume that hidden truth.

An environment executor may internally instantiate the latent fault in order
to produce workflow behavior, but its public treatment interface must expose
only observable execution evidence.

---

## Unknown / out-of-RFS safety control

P09.4 should add a separately scored negative-control population whose true
fault is intentionally outside the treatment Rival Fault Set.

These cases are not part of the primary known-fault Correct Specific Diagnosis
Rate denominator.

Their purpose is to test false certainty.

The desired behavior is conservative non-specific handling such as
`INCONCLUSIVE`, an explicitly registered unknown outcome, or another
preregistered abstention state supported by the final P09.4 contract.

P09.4 must not force an in-RFS diagnosis merely because all known hypotheses
have priors.

If the existing diagnosis contract cannot represent this safely, the required
contract change must be designed and tested before preregistration.

---

## Development and protected split

Development scenarios must be separate from protected evaluation scenarios.

Development cases may be inspected and used to:

- debug environment mechanics;
- validate fault injection;
- validate experiment predictions;
- calibrate reasonable budgets;
- calibrate cost assignments;
- and confirm that comparison arms are executable.

Development outcomes must not be presented as protected evidence.

Protected templates, assignments, seeds, manifests, and sample count must be
frozen only after the environment and evaluator semantics are stable.

---

## Cost and resource accounting

P09.4 should improve on the purely synthetic interpretation risk exposed by
P09.3.

Declared planner cost should be tied to a preregistered rationale based on
expected workflow operations such as tool interactions or workflow steps.

Exact cost values are not frozen in P09.4A1.

Development-only calibration may be used to define a reasonable cost table,
but protected outcomes must never be used to tune it.

The evaluator should report both declared cost and realized resources where
available, including:

- experiment count;
- tool/environment interaction count;
- workflow-step count;
- and any other resource dimension already supported without introducing new
  technology.

Declared synthetic or proxy cost must never be reported as measured production
latency, monetary cost, or compute efficiency.

---

## Metrics

The primary known-fault metric remains Correct Specific Diagnosis Rate.

Required accompanying outcomes should include:

- False Specific Diagnosis Rate;
- INCONCLUSIVE or explicit unknown rate;
- budget-exhausted rate;
- matched-case arm differences;
- per-fault-family results;
- per-template results;
- declared cost;
- realized experiment count;
- realized tool/environment interactions;
- and realized workflow-step count.

The unknown/out-of-RFS control requires its own false-specific or false-certainty
metric.

No naive population p-value or confidence interval should be manufactured from
a constructed controlled population.

---

## Negative controls and ablations

The eventual preregistration should include controls that can distinguish a
real policy effect from an implementation artifact.

Candidate controls include:

- cost-neutral scenarios where C2 and C3 should behave similarly;
- zero-information or dominated probes that should not be preferred when a
  useful affordable probe exists;
- out-of-RFS cases measuring false certainty;
- and matched cases where cost ranking changes but raw information gain does
  not.

The exact control construction must be frozen before protected evaluation.

---

## Fair-budget rule

P09.4 must use fair declared budgets.

C3 may not receive unrestricted experiments while comparison arms are
artificially constrained.

If equal realized cost is impossible because policies choose different
experiments, the asymmetry must be retained and reported rather than hidden.

---

## Invalid-run and no-rerun rule

Operational invalidity must be defined before protected execution.

Wrong diagnoses, poor experiment choices, tool errors produced by the tested
workflow, budget exhaustion, failed recovery, and unfavorable agent behavior
are scientific outcomes unless a preregistered rule specifically establishes
that treatment was not meaningfully executed.

A valid unfavorable protected case must not be rerun to obtain a preferred
outcome.

Any repeated-trial count must be frozen before protected results exist.

---

## P09.4A1 claim boundary

This design document establishes an experimental direction only.

It does not establish that HEAL works on realistic agents.

It does not establish that any P09.4 comparison will favor C3.

It does not establish repair correctness, verification quality, production
reliability, external validity, or state-of-the-art performance.

A null, mixed, weaker, or unfavorable P09.4 result remains valid evidence.

---

## Values intentionally NOT frozen yet

P09.4A1 intentionally does not freeze:

- final scenario/template count;
- protected case count;
- development case count;
- exact trajectory-length threshold;
- exact number of hypotheses per template beyond the design target;
- exact experiment catalogue;
- exact experiment costs;
- exact arm budget;
- exact protected randomization procedure;
- final unknown-fault representation;
- registered numerical pass/fail thresholds;
- or protected artifact paths.

Those choices require development-only feasibility evidence first.

Once protected P09.4 results exist, these decisions may not be retroactively
changed to favor the observed outcome.
