# P09.4 Open-Set Abstention Design

## Status

**DESIGN FROZEN FOR REVIEW — NO CORE IMPLEMENTATION AUTHORITY YET**

This document defines the narrow response to the P09.4A2C3 false-certainty
finding.

It does not modify the core diagnosis contracts or lifecycle.

It does not authorize C0-C3 scientific comparison, protected generation, or
protected execution.

---

## Grounded failure

P09.4A2C3 demonstrated a valid deterministic out-of-RFS development case.

The case produces the same coarse failing report as F1-F5.

P1-P5 all execute real workflow interventions and all return FAIL.

Under the existing closed-world lifecycle, four FAIL observations eliminate
four known hypotheses.

`environment_interaction_fault` becomes the sole surviving known hypothesis.

The existing lifecycle therefore returns `DIAGNOSED` before P5 is executed.

Evaluator truth states that the actual latent cause is outside the Rival Fault
Set.

This is a false-specific diagnosis.

---

## Root cause

The problem is not merely the absence of an `UNKNOWN` enum value.

The deeper issue is closed-world terminal semantics:

a single surviving known hypothesis is treated as sufficient for a specific
diagnosis even when that hypothesis survived only because its competitors were
eliminated.

No direct evidence has yet uniquely confirmed the remaining hypothesis.

---

## Rejected solution: status-only UNKNOWN

Adding `UNKNOWN` or `OUT_OF_RFS` to `DiagnosisStatus` by itself would not solve
the failure.

The current lifecycle would still require a rule telling it when evidence
supports that status instead of the sole surviving known hypothesis.

Therefore A2C4 does not propose a status-only patch.

---

## Rejected solution: synthetic unknown hypothesis

A2C4 does not add a sixth catch-all `unknown` hypothesis to every
`DiagnosisProblem`.

An arbitrary catch-all prediction table would require pretending that Hetren
knows how every unseen fault will respond to every experiment.

That would manufacture evidence semantics rather than solve open-set diagnosis.

---

## Selected design

P09.4 should add an opt-in open-set lifecycle alongside the existing
closed-world lifecycle.

The existing historical functions remain unchanged:

- `replay_observations`;
- `select_next_decision`.

The existing `DiagnosisStatus` values also remain unchanged.

`INCONCLUSIVE` remains the treatment-facing abstention outcome for an
open-set evidence contradiction.

P09.4 should not add a public `UNKNOWN` or `OUT_OF_RFS` status at this stage.

---

## Why the existing closed-world lifecycle must remain unchanged

Prior deterministic demonstrations and P09.3 were designed under closed-world
RFS assumptions.

Changing their lifecycle semantics retroactively would risk altering historical
behavior, hashes, and interpretation boundaries.

The open-set behavior therefore must be explicitly opt-in.

Closed-world callers continue using the existing lifecycle unchanged.

P09.4 uses the new open-set lifecycle only after its development tests pass.

---

## Proposed implementation boundary

The preferred implementation location is a dedicated core module such as:

`packages/core/hetren_diagnosis/open_set.py`

The exact filename may change during implementation review, but the semantic
boundary is fixed:

the feature must not modify historical closed-world decision behavior.

---

## Open-set replay result

The new lifecycle requires an auditable replay result that can distinguish:

1. a valid posterior over at least one still-supported RFS hypothesis;
2. an evidence contradiction where the latest observation is supported by no
   currently viable RFS hypothesis.

A contradiction must be detected before attempting to normalize an all-zero
posterior.

The replay result should retain enough audit information to identify:

- whether contradiction occurred;
- which observation sequence triggered it;
- which experiment produced that observation;
- the observed verdict;
- and the posterior immediately before contradiction.

It must not require evaluator-only latent truth.

---

## RFS-unique confirmation

A specific diagnosis in open-set mode requires more than sole-survivor
elimination.

The surviving hypothesis must have direct RFS-unique support.

For a candidate hypothesis H and an executed experiment E, an observation is
RFS-unique support when:

1. H predicts the observed verdict for E; and
2. no other hypothesis in the original Rival Fault Set predicts that same
   verdict for E.

This rule uses only the treatment-visible registered prediction table and the
actual executed Observation.

It does not use evaluator truth.

---

## Current P09.4 confirmation structure

Under the development prediction matrix:

- P1 PASS uniquely supports F1 tool-selection;
- P2 PASS uniquely supports F2 parameter-transformation;
- P3 PASS uniquely supports F3 sequencing/orchestration;
- P4 PASS uniquely supports F4 state/context;
- P5 PASS uniquely supports F5 environment-interaction.

FAIL observations may eliminate incompatible known hypotheses, but elimination
alone is not sufficient for an open-set specific diagnosis.

---

## Singleton confirmation rule

When exactly one RFS hypothesis remains but it lacks RFS-unique support, the
open-set lifecycle must not immediately return `DIAGNOSED`.

It must first search for an unexecuted experiment capable of producing
RFS-unique confirmation for that candidate.

If more than one such experiment is available, the confirmation-selection rule
must be deterministic:

1. lower declared cost first;
2. experiment key ascending as the final tie-break.

This is a safety-confirmation rule, not a C3 optimization rule.

---

## Budget semantics

A mandatory confirmation experiment consumes ordinary diagnosis budget.

Its declared and actual cost must be counted normally.

If a sole surviving hypothesis is unconfirmed and its required confirmation
experiment is unaffordable because the remaining budget is zero or too small,
the result remains `BUDGET_EXHAUSTED`.

`BUDGET_EXHAUSTED` must not be relabeled as unknown or inconclusive.

The later P09.4 calibration phase must therefore allocate budgets that make
the intended open-set safety test meaningful.

---

## Contradiction rule

When an executed observation is incompatible with every currently viable RFS
hypothesis, the open-set lifecycle must stop.

The treatment-facing terminal status is:

`INCONCLUSIVE`

The audit record should separately identify the reason as an open-set evidence
contradiction.

The implementation must not:

- invent a specific known diagnosis;
- normalize an all-zero posterior;
- silently discard the contradictory observation;
- reinterpret the outcome as `BUDGET_EXHAUSTED`;
- or use evaluator-only out-of-RFS truth to trigger abstention.

---

## No new DiagnosisStatus value

A2C4 intentionally keeps:

- `ACTIVE`;
- `DIAGNOSED`;
- `INCONCLUSIVE`;
- `BUDGET_EXHAUSTED`.

The reason for `INCONCLUSIVE` should be preserved separately in an auditable
open-set replay/decision record.

A dedicated public UNKNOWN status may be reconsidered later only if realistic
validation demonstrates that treatment-facing consumers need to distinguish
open-set contradiction from other forms of inconclusive evidence.

---

## No modification to DiagnosisProblem

A2C4 does not require adding open-set fields to `DiagnosisProblem`.

This avoids changing existing problem canonicalization or historical hashes.

The open-set policy is supplied explicitly to the opt-in lifecycle layer.

---

## No hidden-truth dependency

The open-set lifecycle receives:

- the ordinary `DiagnosisProblem`;
- treatment-visible experiment predictions;
- executed `Observation` records;
- ordinary budget information;
- and the explicit choice to use open-set semantics.

It does not receive:

- the evaluator's true fault label;
- an out-of-RFS boolean;
- protected assignment metadata;
- or a case-to-fault mapping.

The evaluator may later score whether abstention was correct, but evaluator
truth must not cause the abstention.

---

## Expected known-fault development behavior

After implementation, the current five development faults are expected to
require direct confirmation:

- F1: P1 PASS, then specific diagnosis;
- F2: P1 FAIL, P2 PASS, then specific diagnosis;
- F3: P1 FAIL, P2 FAIL, P3 PASS, then specific diagnosis;
- F4: P1 FAIL, P2 FAIL, P3 FAIL, P4 PASS, then specific diagnosis;
- F5: P1 FAIL, P2 FAIL, P3 FAIL, P4 FAIL, P5 PASS, then specific diagnosis.

These are development expectations, not protected scientific results.

---

## Expected out-of-RFS development behavior

For the frozen report-assembly control:

- P1 FAIL;
- P2 FAIL;
- P3 FAIL;
- P4 FAIL;
- P5 FAIL.

After P1-P4, F5 is the sole surviving known hypothesis but remains unconfirmed.

The open-set lifecycle should therefore execute P5 instead of declaring F5.

P5 FAIL is incompatible with the final viable RFS hypothesis.

The resulting terminal status should be `INCONCLUSIVE` with an auditable
open-set contradiction reason.

No known F1-F5 diagnosis should be emitted.

---

## Fairness across future C0-C3 arms

The open-set safety rule is not a C3-only feature.

Any later treatment arm that can emit a specific diagnosis must obey the same
specific-diagnosis support rule.

Mandatory confirmation cost must be counted for every arm that executes it.

C3 must not receive a special abstention safeguard that is withheld from C1 or
C2.

C0 remains trace-only and receives no active diagnostic evidence.

The exact arm semantics are still blocked until open-set development behavior
is implemented and validated.

---

## Required implementation acceptance tests

The future implementation may pass A2C4 only if all of the following hold:

### A — Historical preservation

- the existing closed-world lifecycle remains byte/behavior compatible for
  historical tests;
- existing A2C1-A2C3 development tests remain green;
- P09.3 protected hashes remain exact.

### B — Known-fault correctness

- F1-F5 all still reach correct specific diagnosis;
- each specific diagnosis has RFS-unique supporting evidence;
- F5 requires P5 PASS rather than diagnosis after P1-P4 elimination only.

### C — Out-of-RFS safety

- the report-assembly control executes all five FAIL observations;
- it does not emit a specific F1-F5 diagnosis;
- it terminates `INCONCLUSIVE` after the contradictory P5 FAIL;
- the contradiction is detected without evaluator truth.

### D — Budget integrity

- confirmation experiments consume budget;
- insufficient budget remains `BUDGET_EXHAUSTED`;
- budget exhaustion is never renamed to unknown/inconclusive.

### E — Determinism and auditability

- identical inputs produce identical open-set decisions;
- contradiction metadata is deterministic;
- experiment-state isolation remains preserved;
- no hidden fault identity is read by the open-set selector.

### F — Authority boundary

- no repair authority is introduced;
- no verification authority is introduced;
- no eligibility authority is introduced;
- no protected-result authority is introduced.

---

## Scientific boundary

Passing the future open-set development tests would demonstrate only that the
P09.4 diagnosis lifecycle can abstain safely on the constructed out-of-RFS
control while preserving known-fault diagnosis.

It would not establish real-world open-set robustness.

It would not establish unknown-fault coverage in general.

It would not establish H1.

It would not establish H2-H5.

It would not authorize protected P09.4 execution.

---

## Next gate

After this design is frozen, the next step is:

**P09.4A2C5 — implement the opt-in open-set replay and confirmation lifecycle
as the smallest isolated core increment.**

C0-C3 comparison work remains blocked until that implementation passes the
development acceptance tests above.
