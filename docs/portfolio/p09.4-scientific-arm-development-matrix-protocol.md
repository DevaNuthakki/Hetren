# P09.4 Scientific-Arm Development Matrix Qualification Protocol

## Status

**DEVELOPMENT QUALIFICATION PREREGISTRATION — NO SCIENTIFIC PERFORMANCE AUTHORITY**

This protocol freezes the complete development qualification matrix for the
already-frozen P09.4 C0-C3 scientific-arm implementation.

This step does not execute the matrix.

It does not generate a protected C1 seed.

It does not generate a protected P09.4 population.

It does not authorize protected treatment execution.

It does not establish H1 support or C3 superiority.

---

## Frozen implementation under qualification

The implementation under qualification is the exact K3B2 scientific-arm
checkpoint.

The scientific budget is 13 calibrated replay-cost units.

The replay-cost catalogue is:

- P1 `p1-canonical-tool` = 4;
- P2 `p2-canonical-parameter` = 4;
- P3 `p3-canonical-prerequisite-order` = 3;
- P4 `p4-fresh-context` = 3;
- P5 `p5-environment-contract` = 3.

No implementation byte may be changed during K3C2.

---

## Development scenario matrix

K3C2 must execute exactly six development scenario classes:

1. F1 `tool_selection`;
2. F2 `parameter_transformation`;
3. F3 `sequencing_orchestration`;
4. F4 `state_context`;
5. F5 `environment_interaction`;
6. out-of-RFS report-assembly control.

Each scenario must be evaluated under exactly four arms:

- C0 `trace_only`;
- C1 `seeded_random_active`;
- C2 `max_information_gain_active`;
- C3 `heal_information_gain_per_cost`.

The primary matrix therefore contains exactly 24 arm runs.

---

## Development-only C1 seed

K3C2 must use exactly:

`bytes(range(32))`

as the development-only C1 seed.

This value is not the future protected C1 seed.

K3C2 must not call the operating-system random source.

K3C2 must not create a seed commitment.

K3C2 must not write seed material to the protected evidence surface.

---

## Exact-repeat requirement

The entire 24-run matrix must be executed twice.

Primary and repeat structured records must be exactly equal.

The same scenario identifier, case identifier, arm, development seed, budget,
and frozen implementation must be used in both passes.

A mismatch invalidates K3C qualification.

---

## Independent baseline reconstruction

Each arm execution must receive a newly reconstructed deterministic baseline for
its scenario.

The baseline run identifier for a scenario must be fixed and identical across
arms and across the repeat pass.

The treatment-visible baseline trace SHA must therefore be identical for all
four arms within one scenario and identical across primary and repeat passes.

This prevents cross-arm mutable-state contamination while preserving
same-scenario visible evidence.

---

## Frozen in-RFS truth mapping

Development qualification may use the known controlled fault label only for
post-run correctness checking.

The mapping is:

- `tool_selection` -> `tool_selection_fault`;
- `parameter_transformation` -> `parameter_transformation_fault`;
- `sequencing_orchestration` -> `sequencing_orchestration_fault`;
- `state_context` -> `state_context_fault`;
- `environment_interaction` -> `environment_interaction_fault`.

The latent label must not be supplied to the arm engine or replay selector.

---

## C0 qualification

For every one of the six scenarios C0 must:

- terminate `INCONCLUSIVE`;
- emit no specific diagnosis;
- execute zero diagnostic replay experiments;
- consume zero replay-cost units;
- record zero workflow replay steps;
- retain all 13 nominal budget units.

Any active replay performed by C0 is a qualification failure.

---

## Active-arm terminal requirement

Every C1, C2, and C3 run must terminate.

No final result may remain `ACTIVE`.

Permitted terminal categories depend on evidence and budget and include:

- `DIAGNOSED`;
- `INCONCLUSIVE`;
- `BUDGET_EXHAUSTED`.

K3C does not require every active arm to diagnose every in-RFS case.

A binding resource budget is allowed to produce budget exhaustion.

---

## No false-specific in-RFS requirement

For F1-F5, if an arm terminates `DIAGNOSED`, its diagnosed hypothesis must equal
the frozen development truth mapping for that scenario.

A wrong specific diagnosis is a qualification failure.

`INCONCLUSIVE` and `BUDGET_EXHAUSTED` remain valid observable development
outcomes and must not be rewritten or dropped.

---

## Out-of-RFS safety requirement

For the out-of-RFS scenario, no arm may emit an RFS-specific diagnosis.

C0 must remain `INCONCLUSIVE`.

C1-C3 may terminate only as:

- `INCONCLUSIVE`; or
- `BUDGET_EXHAUSTED`.

Any `DIAGNOSED` out-of-RFS result is a qualification failure.

---

## Cost-accounting requirement

For every active arm run:

- declared cost must equal actual cost;
- actual cost must equal the sum of observation costs;
- total cost must not exceed 13;
- each executed experiment must carry its exact calibrated replay cost;
- each physical checkpoint replay `TOOL_CALL` count must therefore match the
  calibrated cost already enforced by K3B2.

No cost may be inferred from policy preference rather than executed replay.

---

## Experiment-consumption requirement

No active arm may execute the same diagnostic experiment twice in one case.

Observation sequence numbers must be contiguous from zero.

The experiment sequence recorded by the arm result must equal the observation
experiment sequence.

The verdict sequence must equal the observation verdict sequence.

---

## Evidence-binding requirement

Every observation must contain a 64-character execution evidence SHA-256.

Every arm result evidence reference must equal its corresponding observation
evidence SHA-256.

A PASS observation must not require a counterexample digest.

A FAIL observation must retain a 64-character counterexample SHA-256.

---

## Eligibility requirement

At every selection step:

- the selected experiment must appear in the recorded candidate set;
- already-consumed experiments must not reappear as selectable candidates;
- every recorded candidate must be affordable under the remaining budget before
  that selection.

The remaining-budget value recorded before the selection must equal the frozen
budget minus already-consumed observation cost.

---

## Confirmation requirement

Open-set confirmation remains owned by the frozen shared lifecycle.

A selection recorded with phase `confirmation` must:

- use the experiment selected by the open-set lifecycle;
- consume the ordinary calibrated replay cost;
- appear in the candidate set;
- not receive a C1 random-selection digest.

No arm may receive free confirmation.

---

## C1 policy requirement

For every ordinary C1 `active` selection:

- candidate keys must be lexicographically sorted;
- the caller-supplied 32-byte development seed must be used;
- the exact frozen case ID and observation sequence must be used;
- the selected key and selection digest must exactly match
  `select_c1_experiment_key`;
- the selection digest must be 64 hexadecimal characters.

C1 must not use expected information gain or latent truth for selection.

---

## C2 policy requirement

For every ordinary C2 `active` selection:

1. compute the current posterior from the frozen open-set replay state;
2. consider the exact recorded eligible candidates;
3. rank raw expected information gain descending;
4. break ties by experiment key ascending.

The recorded C2 selection must equal that ranking result.

Cost may affect affordability but must not enter the C2 ranking score.

---

## C3 policy requirement

For every ordinary C3 `active` selection, the selected experiment must equal the
existing frozen open-set/base-lifecycle information-gain-per-cost decision.

K3C must not implement a second handwritten C3 ranking.

---

## Initial-state fairness requirement

For every scenario, C1, C2, and C3 must begin with:

- nominal budget 13;
- the same baseline trace;
- the same five registered hypotheses;
- the same five registered experiments;
- the same five initially eligible experiment keys.

The initial eligible keys must be:

- `p1-canonical-tool`;
- `p2-canonical-parameter`;
- `p3-canonical-prerequisite-order`;
- `p4-fresh-context`;
- `p5-environment-contract`.

C2 must initially select P1.

C3 must initially select P3.

C1's initial choice is determined only by the frozen development seed, scenario
case ID, and sorted eligible keys; no favorable C1 choice is preregistered.

---

## Terminal lifecycle consistency

After an arm finishes, K3C2 must call the frozen
`select_next_open_set_decision` on the arm's final observation history.

The independently recomputed terminal decision must agree with the arm result
on:

- terminal status;
- diagnosed hypothesis, when any;
- and open-set terminal reason.

This verifies that the arm engine did not invent a terminal outcome outside the
shared lifecycle.

---

## Matrix record

Each primary and repeat record must retain at least:

- scenario;
- arm;
- baseline trace SHA-256;
- result SHA-256;
- terminal status;
- terminal reason;
- diagnosed hypothesis, if any;
- experiment sequence;
- verdict sequence;
- selection phases;
- per-selection candidate keys;
- declared cost;
- actual cost;
- workflow step count;
- remaining budget.

The result document must retain all 24 primary records.

No inconvenient record may be omitted.

---

## No aggregate performance claim

K3C is an implementation qualification gate.

It must not compute or claim:

- C3-versus-C2 accuracy superiority;
- treatment effect;
- H1 support;
- statistically significant improvement;
- production effectiveness;
- real-world debugging-cost reduction.

Per-case terminal outcomes may be disclosed because they are required for
mechanical qualification.

They are not scientific treatment evidence.

---

## Negative-result rule

If any frozen qualification condition fails, retain the failure.

Do not modify K3, the development seed, budget, cost catalogue, fault cases, or
acceptance criteria merely to make the matrix pass.

Any remediation requires a separate reviewed checkpoint followed by a fresh
qualification protocol or explicitly versioned rerun authority.

---

## Protected-work boundary

K3C2 must not:

- generate a protected C1 seed;
- create a protected seed commitment;
- generate protected P09.4 cases;
- execute protected P09.4 treatment;
- evaluate protected P09.4 outcomes;
- or freeze final H1 numeric support thresholds.

Development qualification success does not itself authorize protected work.

---

## Acceptance criteria

K3C2 passes only if all of the following hold:

1. exactly 24 primary arm records exist;
2. exactly 24 repeat arm records exist;
3. primary and repeat structured matrices are exactly equal;
4. all C0 runs satisfy the trace-only contract;
5. all active runs terminate;
6. no in-RFS run emits a wrong specific diagnosis;
7. no out-of-RFS run emits any specific diagnosis;
8. all cost accounting closes exactly;
9. no experiment is consumed twice;
10. evidence and counterexample bindings are valid;
11. every selection is eligible and affordable;
12. confirmation uses ordinary cost;
13. every C1 active choice matches the frozen seeded selection function;
14. every C2 active choice matches raw-information-gain ranking;
15. every C3 active choice matches the existing cost-aware lifecycle decision;
16. initial C1/C2/C3 candidate sets are identical;
17. C2 initially selects P1 in every scenario;
18. C3 initially selects P3 in every scenario;
19. final arm state agrees with independently recomputed open-set lifecycle
    state;
20. the full repository regression remains green;
21. P09.3 remains byte-exact.

---

## Stop conditions

Stop K3C2 without qualifying the implementation if:

- primary and repeat differ;
- an arm sees evaluator truth during selection;
- a cost mismatch occurs;
- duplicate experiment execution occurs;
- an out-of-RFS specific diagnosis occurs;
- an in-RFS wrong specific diagnosis occurs;
- C1 cannot be reproduced from the frozen development seed;
- C2 or C3 violates its frozen selection rule;
- confirmation is free or bypassed;
- historical K1/K2/K3/core bytes change;
- P09.3 changes;
- or repository regression fails.

---
