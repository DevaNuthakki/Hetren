# P09.4 K5D-4D2 — Protected C1 Architecture Options

**Status:** DESIGN OPTIONS DRAFT — NOT APPROVED FOR IMPLEMENTATION
OR PROTECTED SCIENTIFIC EXECUTION

**Repository basis:** `150195417edb58546438852e8f147d89854e6fc9`

**Scientific authority:** Frozen P09.4 protected-study preregistration.

**Requirements basis:** K5D-4C protected-readiness gap matrix,
C1-01 through C1-17 and design areas D1 through D6.

This document evaluates engineering approaches. Nothing here
authorizes a real seed, protected population, treatment, or evaluation.

## 1. Design question

Select an implementation architecture capable of supporting a
separately authorized, irreversible, auditable protected C1
seed-commitment operation.

The implementation must respect the frozen scientific protocol
without turning development fixtures into protected evidence.

This is an engineering design decision, not a scientific result.

## 2. Non-negotiable protocol boundaries

The frozen requirements include:

- Exactly one 32-byte protected C1 seed from OS cryptographic
  randomness, generated during its separately authorized gate.
- A public SHA-256 commitment with private raw seed material
  restricted to the authorized treatment-evidence boundary.
- No printing, rerolling for convenience, or reuse of the
  development or protected generation seed.
- The same C1 seed across all protected C1 cases, with frozen
  case-ID and selection-sequence domain separation.
- Distinct generation and C1 seeds from separate OS-random calls.
- Different final commitments and execution blocking upon
  collision or raw-seed identity.
- Separate K5D, K5E, and downstream execution authorizations.

Engineering recommendations below are not frozen protocol clauses.

## 3. Option A — Simple local file-based controller

Design:
- One designated filesystem directory for the C1 identity.
- Exclusive directory claim before seed generation.
- STARTED, SUCCEEDED, and FAILED disposition records.
- Files for private seed and public commitment.
- Explicit operator approval checked before identity claim.

Advantages:
- Small implementation and limited dependency surface.
- Easy to understand, reproduce, and test.
- Reuses conceptual lessons from K5D-3 without copying
  development fixture paths into protected execution.

Limitations:
- Path-based checks are vulnerable to TOCTOU races.
- Arbitrary alternate roots can bypass local uniqueness.
- Approval-file existence alone is not genuine
  independently verifiable authorization.
- File permissions alone do not enforce immutability.
- Recovery after uncertain durability needs stronger rules.

Assessment: useful baseline, but inadequate without additional
controls for the targeted protected-readiness standard.

## 4. Option B — Hardened local one-shot controller

Design:
- One explicitly approved canonical study identity and root.
- Trusted, access-controlled parent directory.
- Descriptor-relative filesystem operations where supported.
- Non-following and exclusive creation to reduce symlink races.
- Separate authorization-verification stage before claim.
- Irreversible claim, durable STARTED record, then OS randomness.
- Private raw seed and public commitment persisted separately.
- Conservative handling of incomplete and FAILED attempts.
- Frozen lineage and a human-reviewable evidence record.

Advantages:
- Matches the local terminal-driven portfolio workflow.
- Strong, inspectable one-shot engineering evidence.
- Deterministic synthetic fault-injection tests are feasible.
- Avoids mandatory external cloud services.
- Separates design, testing, authorization, and execution.

Limitations:
- Descriptor-relative operations need platform capability checks.
- Portable filesystem durability is not guaranteed.
- A hostile same-user process may exceed the declared trust model.
- Replicated repositories or different canonical roots can create
  separate identities without an external coordinating authority.
- Authorization authenticity depends on the actual issuer,
  verifier, and protected trust root.
- Adds meaningful implementation and review complexity.

Assessment: PROVISIONALLY PREFERRED, conditional on D1-D6
resolution and independent engineering qualification.

## 5. Option C — Externally managed secret controller

Design:
- Use an external secrets service or key-management system.
- Bind an approved one-shot identity to a managed access policy.
- Store or release raw seed material only to an authorized
  treatment-execution boundary.
- Retain separate local public commitment/disposition evidence.

Advantages:
- Potentially stronger central identity and access policy.
- Managed audit controls and administrative separation.
- Easier to coordinate an identity across multiple machines
  if the service explicitly enforces that contract.

Limitations:
- Authentication, connectivity, cloud availability, and cost.
- More complicated deterministic test and recovery behavior.
- Service access logging does not by itself prove one-shot
  randomness or immutable scientific provenance.
- Could introduce disproportionate infrastructure complexity.
- A service that permits overwriting or duplicating secrets
  does not automatically meet the frozen one-shot requirement.

Assessment: legitimate alternative where cross-machine control
and operational separation justify the dependency; not yet
necessary for this single-workspace engineering milestone.

## 6. Qualitative comparison

| Criterion | A: Simple local | B: Hardened local | C: Managed secret |
|---|---|---|---|
| Local reproducibility | Strong | Strong with platform checks | Service-dependent |
| Filesystem race defenses | Limited | Stronger, not absolute | Depends on local integration |
| Authorization assurance | Weak without added controls | Explicit verification design needed | Provider policy plus verification |
| One-shot identity scope | One location | Approved canonical root | Potentially multi-machine |
| Crash-state visibility | Needs work | Designed explicitly | Service-specific |
| Operational dependencies | Low | Moderate | High |
| Testability | High | High with fault injection | Requires service emulation/integration |
| Portfolio engineering value | Moderate | High | High but broad |
| Current readiness | Not approved | Not approved | Not approved |

These are reasoned qualitative judgments, not experimentally
measured performance, reliability, or security results.

## 7. Provisional selection

**Recommend Option B for further design qualification.**

Why:
1. It directly addresses the observed K5D-3 filesystem limitations.
2. It keeps scientific control boundaries visible and reviewable.
3. It supports meaningful fault-injection and lifecycle testing.
4. It avoids cloud infrastructure unrelated to the core hypothesis.
5. It demonstrates backend and infrastructure engineering depth
   without expanding the scientific project scope.

Selection is provisional. Option B is not authorized to execute.

If the platform lacks necessary safe filesystem primitives, or if
the trust model requires global cross-machine uniqueness, revisit
Option C or a suitably constrained alternate design.

## 8. D1-D6 recommended engineering controls

### D1. Authorization and execution separation

Proposal:
- Define an explicit, reviewable approval record.
- Bind it to study identity, protocol digest, source identity,
  approved operation, intended root, and authorized operator.
- Verify its authenticity and scope before claiming identity.
- Keep approval issuance distinct from seed-generation execution.
- Do not mistake an unsigned editable JSON file for independent
  authorization evidence.
- A signature-based design is only meaningful if the verifier
  trusts a separately controlled signing key.

Open decision: approval issuer, verifier, trust anchor, revocation,
expiry, and how a single-person portfolio workflow documents
governance without claiming nonexistent external independence.

### D2. Canonical identity and artifact schema

Proposal:
- Specify exactly one canonical protected identity per study version.
- Specify a controlled root with no alternative root override
  for the real protected operation.
- Bind the identity to the frozen study protocol.
- Separate public commitment/disposition evidence from private
  treatment-boundary seed material.
- Record approved schema version and ownership explicitly.

A candidate location under the existing P09.4 artifact namespace
may be reviewed, but this document does not approve any path.

Open decision: canonical study root, schema, version and retention
policy, and what protects identity across copies or hosts.

### D3. Irreversible lifecycle and recovery

Proposed lifecycle:

PREFLIGHT (no claim and no randomness)
-> APPROVED (valid independent authorization evidence)
-> CLAIMED (identity irreversibly consumed)
-> STARTED (durable record before randomness)
-> PRIVATE_SEED_PERSISTED
-> PUBLIC_COMMITMENT_PERSISTED
-> SUCCEEDED.

Any failure after CLAIMED transitions to FAILED where a durable
record can be written; otherwise the claimed/incomplete identity
remains consumed and requires investigation, never automatic reroll.

A process crash can leave intermediate files even when Python
cleanup is correct. File visibility is not proof of confirmed
durability. Recovery must never call the seed factory again for
the same claimed identity.

Open decision: target filesystem guarantees, failure disposition
semantics, recovery access policy, and evidence retention.

### D4. Filesystem trust and threat model

Proposed controls to qualify:
- Trusted parent ownership and restrictive directory permissions.
- Exclusive, non-following, descriptor-relative operations.
- Verification of actual platform support for `dir_fd`,
  `O_NOFOLLOW`, directory sync, and atomic publication behavior.
- No path alias or fallback that silently relaxes checks.
- Defined concurrency and competing-process model.
- Explicit abort if required platform operations are unsupported.

Directory `fsync` and file `fsync` do not provide a universal
power-loss durability guarantee. Platform and filesystem semantics
must be verified rather than assumed.

Open decision: trusted filesystem, backup/snapshot exposure,
same-user adversary scope, and macOS-specific durability guarantees.

### D5. OS-random provenance and non-disclosure

Proposal:
- A narrowly controlled OS-random capability supplies exactly
  32 bytes only after durable identity/STARTED qualification.
- Development testing substitutes synthetic fixtures.
- Raw seed never enters terminal output, logs, public JSON,
  error messages, or exception formatting.
- Public evidence contains only approved nonsecret metadata and
  a SHA-256 commitment.
- Record the operation and source mechanism without recording
  raw seed material in public evidence.

Separate OS-random invocation evidence must be maintained for
the later generation seed. Distinct commitments alone cannot prove
independent operating-system randomness calls.

Open decision: production randomness adapter, provenance record,
sensitive exception handling, and private access controls.

### D6. Frozen lineage and downstream handoff

Proposal:
- Verify frozen protocol SHA256 and approved source identity
  before entering the irreversible operation.
- Bind lineage and schema into the public commitment record.
- Preserve necessary evidence for future K5E independence checks.
- Do not allow K5D to authorize K5E or treatment implicitly.

Open decision: approved version binding, later comparison interface,
integrity verification, and protected treatment handoff.

## 9. Required development qualification before real use

Future implementation acceptance tests should include:
- Invalid or absent authorization fails before identity claim.
- Wrong protocol/source/study identity fails closed.
- Concurrent claims result in at most one consumed identity
  within the declared canonical authority boundary.
- STARTED is durable before real randomness would be invoked.
- Every post-claim failure prevents reroll.
- Interrupted private/public writes preserve the identity.
- Raw seed does not enter public evidence or logs.
- Permission, symlink, race, and path-validation failures.
- Unsupported filesystem primitives fail closed.
- Recovery from incomplete claims does not regenerate seeds.
- Cross-root and cross-host limitations are documented.
- Full existing active regressions remain preserved.

These tests must use synthetic seeds and non-protected fixtures.

A passing development suite does not authorize real protected use.

## 10. Architecture decision gates

**AD-1:** Audit the frozen requirements and Option B assumptions.

**AD-2:** Validate filesystem capabilities and threat model,
using read-only platform inspection.

**AD-3:** Specify approval evidence, canonical identity,
schema, and recovery contract; obtain a separate design review.

**AD-4:** Implement development-only controls and negative tests,
with no real seed creation.

**AD-5:** Complete fault injection, regression, and frozen-evidence
preservation review.

**AD-6:** Seek separately explicit protected K5D authorization
only after the qualified design has been reviewed.

No gate automatically approves a later gate.

## 12. K5D-4D2D Observed Platform Evidence

**Status: DEVELOPMENT-ONLY OBSERVATION — NOT PROTECTED QUALIFICATION**

The K5D-4D2D probe used fixed, nonsecret synthetic fixture
bytes in a disposable operating-system temporary directory
outside the Hetren repository.

The inspected Python environment was Python 3.12.7 on Darwin
24.4.0, x86_64.

The P09.4 artifact namespace was absent and was not created.

### 12.1 Observed successful operations

The synthetic probe observed:

- Exclusive directory creation rejected a duplicate claim.
- Descriptor-relative directory opening succeeded.
- Exclusive file creation rejected an existing destination.
- A synthetic file was created with restricted access.
- File `fsync` returned success.
- macOS `F_FULLFSYNC` returned success.
- Directory `fsync` returned success on inspected descriptors.
- Descriptor-relative, non-replacing hard-link publication
  succeeded and preserved inode identity.
- A duplicate hard-link destination was rejected.
- `O_NOFOLLOW` rejected a final-component symbolic link.
- The temporary fixture was completely removed afterward.

These results establish successful syscall behavior for the
specific tested synthetic fixture only.

The fixture filesystem was not independently established as
identical to the future protected target filesystem.

The volume type was not confirmed by the earlier metadata
inspection.

### 12.2 Observed path-confinement limitations

A path containing an intermediate symbolic link was followed
even though `O_NOFOLLOW` was supplied for the final component.

Opening `..` relative to a directory descriptor reached the
parent directory.

Therefore:

- `dir_fd` alone does not provide filesystem confinement.
- Final-component `O_NOFOLLOW` is insufficient for paths
  containing untrusted intermediate components.
- Descriptor-relative operations must be combined with
  constrained path-component handling.
- Untrusted absolute paths, empty components, `.`, and `..`
  must not be accepted as protected relative components.
- Every required directory component must be independently
  opened and validated without following symbolic links.
- The root descriptor must itself originate from an approved
  trusted location.

These are engineering design requirements recommended in
response to the probe, not additional frozen scientific rules.

Even component-by-component traversal does not automatically
defend against hostile same-user processes, mount changes,
or every filesystem race.

### 12.3 Durability interpretation

A successful `fsync` or `F_FULLFSYNC` call is not a completed
power-loss recovery test.

The probe did not establish:

- durability under actual power interruption;
- crash consistency across all publication stages;
- recovery after process termination;
- correctness under adversarial concurrent mutation;
- behavior on every supported filesystem;
- or cross-machine one-shot uniqueness.

Incomplete or uncertain persistence must never become a
reason to regenerate a claimed protected seed.

### 12.4 Bounded trust model for Option B

Option B remains the preferred candidate for subsequent
development-only qualification, assuming:

1. One explicitly designated local study identity and root.
2. A trusted operating-system user and controlled filesystem.
3. Restricted, validated directory-descriptor traversal.
4. No arbitrary caller-selected root for a future real operation.
5. Conservative no-reroll handling after identity claim.
6. Synthetic negative tests for unsupported operations,
   path manipulation, contention, and failure states.
7. A separate, authentic authorization and evidence contract.

This is a bounded local trust model, not a claim of protection
against all processes running with the same user authority.

Cross-host coordination and global identity uniqueness remain
outside the currently demonstrated guarantees.

### 12.5 Authorization limitation

A signature or approval file is not independent authorization
unless the issuing authority and its trust anchor are genuinely
separate from the untrusted execution capability.

For a single-developer portfolio environment, test fixtures
can demonstrate verification mechanics but must not be
represented as external or independently issued approval.

No real authorization issuer, verifier, trust anchor, or
protected approval record has yet been approved.

### 12.6 Engineering scope decision

Retain Option B for narrowly scoped engineering design work.

Do not build a general-purpose secrets manager, introduce a
mandatory cloud dependency, or expand into protected scientific
execution merely to demonstrate filesystem mechanisms.

Future implementation increments must remain synthetic-only
until the design, provenance, identity, recovery, and authority
requirements have been separately satisfied and reviewed.

The next design priority is D1 authorization semantics and D2
canonical identity/schema, not another general filesystem
feature expansion.
