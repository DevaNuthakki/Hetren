# P09.4 Development Cost and Budget Calibration Protocol

## Status

**PRE-MEASUREMENT DEVELOPMENT PROTOCOL — NO SCIENTIFIC COMPARISON AUTHORITY**

This document freezes how P09.4 diagnostic experiment costs and candidate
budgets will be measured and derived before any C0-C3 scientific comparison.

No calibration measurements are recorded in this document.

No protected P09.4 population exists.

No protected generation or execution is authorized.

---

## Readiness basis

P09.4A2C6A verified all A2B development acceptance gates A-J.

The richer deterministic environment is therefore mechanically ready for
development-only calibration.

The current development values:

- `cost_units = 1` for each probe;
- `budget_units = 5`;

remain provisional mechanics.

They are not scientifically calibrated P09.4 values.

---

## Calibration purpose

The purpose of calibration is to derive declared experiment costs from
observable execution resource use rather than from desired C3 behavior.

Calibration must answer:

1. whether P1-P5 actually have different executable resource costs;
2. what deterministic integer cost units those resource costs justify;
3. what mechanical diagnosis-budget landmarks follow from those costs;
4. whether a meaningful cost-aware C3 versus raw-information-gain C2
   comparison is identifiable in the current environment.

---

## Non-objectives

Calibration must not:

- compare C0, C1, C2, and C3 outcome quality;
- choose costs to make C3 outperform C2;
- choose a budget after inspecting C0-C3 accuracy;
- inspect future protected outcomes;
- create a protected case population;
- select final H1 support thresholds;
- estimate real production dollars, latency, GPU cost, or cloud spend;
- or introduce machine-dependent wall-clock timing as scientific evidence.

---

## Frozen development calibration cases

Calibration measurements will use exactly seven development case classes:

- canonical no-fault control;
- F1 tool-selection;
- F2 parameter-transformation;
- F3 sequencing/orchestration;
- F4 state/context;
- F5 environment-interaction;
- out-of-RFS report-assembly control.

These cases are development fixtures only.

Their latent labels may be used to organize calibration records because
calibration is not a protected treatment evaluation.

Latent labels must not influence the measured resource values.

---

## Frozen experiment catalogue

Calibration will measure exactly the five existing development probes:

- P1 `p1-canonical-tool`;
- P2 `p2-canonical-parameter`;
- P3 `p3-canonical-prerequisite-order`;
- P4 `p4-fresh-context`;
- P5 `p5-environment-contract`.

No probe may be added, removed, or assigned a special cost during the
measurement pass.

---

## Frozen measurement matrix

Every P1-P5 probe will be executed once against every one of the seven
development case classes.

The primary calibration matrix therefore contains:

`7 case classes × 5 probes = 35 deterministic executions`

The measurement pass may also repeat this matrix once solely to verify
deterministic reproducibility.

A reproducibility repeat must not be averaged with the primary matrix.

If the repeated resource record differs from the primary deterministic
measurement, calibration fails and stops.

---

## Resource counters

For every executed probe, calibration must record:

- experiment key;
- development case class;
- executed verdict;
- diagnostic experiment count;
- tool/environment interaction count;
- workflow event/step count;
- trace SHA-256;
- execution-evidence SHA-256;
- current provisional declared cost.

The verdict is recorded only for audit context.

The verdict must not influence calibrated cost.

---

## Primary cost quantity

The primary physical cost quantity for this deterministic environment is:

**tool/environment interaction count**

Reason:

tool and environment interactions are the clearest executable analogue of
external diagnostic work currently represented by the environment.

Workflow event count is retained as a secondary structural counter.

The protocol does not assign an arbitrary exchange rate between one tool
interaction and one internal trace event.

---

## Per-probe raw cost rule

For each probe E:

`raw_tool_cost(E) = maximum tool/environment interaction count observed for E
across the seven frozen development case classes.`

The maximum is used rather than the minimum or outcome-conditioned value so
the declared cost is conservative and known before protected evaluation.

If a probe's tool-interaction count varies by case, that variability must be
reported explicitly.

No case-specific treatment cost may later be selected using hidden truth.

---

## Secondary structural audit

For each probe, calibration will also report:

- minimum workflow-step count;
- maximum workflow-step count;
- whether workflow-step count is invariant across case classes.

Workflow-step count is an audit metric in this calibration version.

It is not used to break a tie between probes with equal tool-interaction
cost.

This prevents an arbitrary hand-chosen scalar weighting from manufacturing
cost asymmetry.

---

## Integer normalization rule

If the five raw tool costs are positive integers and at least two probes have
different raw tool costs, the normalized declared costs are:

`normalized_cost(E) = raw_tool_cost(E) / gcd(raw_tool_cost(P1..P5))`

The result must remain an exact positive integer.

No rounding, clipping, manual weighting, or result-driven adjustment is
allowed.

---

## Equal-cost degeneracy rule

If:

`raw_tool_cost(P1) = raw_tool_cost(P2) = ... = raw_tool_cost(P5)`

then the calibrated probe catalogue is cost-degenerate.

In that case:

- every normalized probe cost is `1`;
- C3 information-gain-per-cost ranking collapses to raw information-gain
  ranking when all other eligibility conditions are equal;
- the current probe catalogue cannot support a scientifically meaningful
  cost-aware C3-versus-C2 mechanism comparison;
- no artificial unequal cost may be assigned;
- workflow-step tie-breaks must not be invented after observing the tie;
- C0-C3 scientific comparison remains blocked;
- and P09.4 must return to development design to create genuinely unequal
  executable diagnostic costs if a cost-aware comparison remains required.

An equal-cost result is a valid calibration result.

It must be retained rather than optimized away.

---

## Non-degenerate cost rule

If at least two probes have different measured raw tool costs, calibration
may proceed with the exact normalized integer costs.

Those costs become candidate preregistration inputs only after a separate
calibration-result review.

They do not become protected values merely because this development
measurement succeeded.

---

## Outcome-independence rule

A probe's declared cost must not depend on whether its diagnostic execution
returns PASS or FAIL.

If PASS and FAIL cases cause different resource counts for the same probe,
the conservative maximum across frozen development cases is used.

This preserves ex ante treatment cost and prevents latent truth from changing
the planner's declared experiment price.

---

## Determinism rule

The 35-execution calibration matrix must be reproducible.

For identical case/probe/run inputs, the following must remain exact:

- verdict;
- tool/environment interaction count;
- workflow-step count;
- trace SHA-256;
- execution-evidence SHA-256.

A deterministic mismatch invalidates calibration.

Calibration must stop before cost freezing.

---

## Budget calibration landmarks

A2C6C will compute mechanical budget landmarks only after measured probe costs
exist.

The required landmarks are:

### Full catalogue budget

`B_full = sum(normalized_cost(P1..P5))`

This is the cost required to execute every registered probe once.

It is also the mechanical upper bound required by the current five-probe
out-of-RFS contradiction path.

### Cheapest-k ladder

Sort normalized probe costs ascending, breaking ties by experiment key.

For k = 1..5:

`B_k = sum(cost of the k cheapest probes)`

This ladder describes the mechanical affordability surface only.

It is not a scientific-performance result.

### Confirmation integrity

Mandatory open-set confirmation consumes ordinary budget.

If a future selected budget cannot afford required confirmation, the valid
terminal state remains `BUDGET_EXHAUSTED`.

Calibration must not grant free confirmation.

---

## Final budget remains unfrozen

Neither `B_full` nor any `B_k` automatically becomes the final P09.4
scientific budget.

A later preregistration step must choose the evaluation budget before protected
generation and without inspecting protected outcomes.

The choice must be justified using:

- calibrated executable costs;
- required open-set safety semantics;
- intended comparison question;
- and fair availability of budget across treatment arms.

It must not be justified by whichever budget makes C3 look strongest in
development outcome comparisons.

---

## C0-C3 prohibition during calibration

A2C6C must not run a C0-C3 batch comparison.

It must not calculate:

- C3 minus C0 accuracy;
- C3 minus C1 accuracy;
- C3 minus C2 accuracy;
- arm-specific success rates;
- false-specific-rate differences between arms;
- or candidate H1 support thresholds.

The only purpose of A2C6C is resource calibration and the cost-identifiability
gate.

---

## Open-set safety during calibration

The out-of-RFS development control is included to ensure probe resource costs
are measured on the contradiction path.

Its evaluator-known status must not be provided to the open-set core.

The calibration record may state that all P1-P5 FAIL for this development
control because that behavior was already established before calibration.

No new scientific out-of-RFS effectiveness claim may be made.

---

## Wall-clock and machine-resource exclusion

A2C6C will not use wall-clock duration, CPU percentage, memory usage, cloud
pricing, GPU usage, or network latency as calibrated scientific costs.

Those quantities are not currently represented by a controlled reproducible
measurement contract.

Introducing them would require a separate technology and measurement review.

---

## Calibration output requirements

A2C6C must produce a development calibration record containing:

- exact source checkpoint;
- exact relevant source hashes;
- exact 35-row primary measurement matrix;
- deterministic-repeat verification;
- per-probe raw tool cost;
- per-probe workflow-step range;
- normalized integer cost candidate, if non-degenerate;
- `B_full` and the `B_k` mechanical budget ladder, if normalization is valid;
- cost-degeneracy verdict;
- cost-aware-comparison identifiability verdict;
- explicit stop/pass decision;
- and the scientific authority boundary.

---

## Calibration pass condition

Calibration is mechanically valid when:

- all frozen development executions complete;
- resource measurements are deterministic;
- the resource record is complete;
- costs are derived exactly according to this protocol;
- no outcome-dependent cost assignment occurs;
- and historical/protected evidence remains unchanged.

Mechanical calibration validity does not imply cost-aware comparison
identifiability.

---

## Calibration stop conditions

A2C6C must stop before any C0-C3 scientific work if:

- deterministic resource counts are not reproducible;
- resource accounting is incomplete;
- any cost would require arbitrary manual weighting;
- any cost assignment depends on latent fault truth or PASS/FAIL outcome;
- or the equal-cost degeneracy rule is triggered.

A stop is a valid development result.

---

## Claim boundary

A successful calibration measurement would establish only a reproducible
development cost model for this deterministic environment.

It would not establish:

- H1 support;
- C3 superiority;
- real-world economic cost;
- latency improvement;
- model-backed robustness;
- production efficiency;
- repair correctness;
- verification quality;
- or protected P09.4 validity.
