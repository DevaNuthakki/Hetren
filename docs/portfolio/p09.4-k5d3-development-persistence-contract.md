commitment persistence.

## 4. Required operation ordering

Before identity claim:

- Validate development artifact root and its isolation.
- Validate lineage and caller-supplied configuration.
- Validate callable seed factory.
- Reject unsafe paths and symbolic-link boundaries.
- Do not invoke the seed factory.
- Do not create C1 identity for failed preflight.

After successful preflight:

1. Claim exactly one development identity atomically.
2. Synchronize the identity claim to its parent directory.
3. Create the public evidence directory.
4. Durably persist STARTED disposition.
5. Create the private treatment directory.
6. Invoke the injected synthetic seed factory exactly once.
7. Validate that the result is exactly 32 bytes.
8. Persist synthetic raw seed privately.
9. Build the development-only C1 commitment.
10. Persist the public commitment without raw seed.
11. Durably replace STARTED with SUCCEEDED.

Seed-factory invocation must never precede the durable STARTED
disposition.

## 5. Irreversible identity semantics

An identity already present must be rejected before calling the
seed factory, regardless of disposition status.

Successful, failed, interrupted, and incompletely initialized
identities must not be silently rerolled.

An exception after identity claim consumes the identity.

Failure handling must attempt to persist a FAILED disposition.

Failure to persist FAILED must still leave the claimed identity
consumed and return an explicit error.

No cleanup may remove the claimed identity to permit retry.

## 6. Private and public evidence

Synthetic raw seed bytes belong only inside the private
development treatment directory.

The public development commitment contains only permitted
lineage and the SHA256 commitment.

Neither the raw seed nor its hexadecimal representation may
appear in public files, returned public records, or logs.

Private directories must be restrictive, targeting mode 0700.

Private files must be restrictive, targeting mode 0600.

File creation and disposition replacement require atomic,
durable filesystem operations.

The implementation must not modify or import private K5C
helpers merely to bypass their ownership boundary.

## 7. Seed independence

K5D precedes K5E.

The real generation seed does not exist at K5D development
qualification.

No development test may use real protected seed material.

A synthetic equality/collision test may validate comparison
mechanics, but it does not establish independent OS-random
provenance for future real seeds.

The eventual real C1 and generation seed commitments must be
compared after both exist and before protected execution.

## 8. Development regression matrix

Tests must qualify at least:

- preflight rejects unsafe paths without consuming identity;
- STARTED is durable before seed-factory invocation;
- synthetic seed factory is called once on success;
- duplicate identity is rejected before seed generation;
- an interrupted STARTED identity prevents reroll;
- factory exceptions consume identity and retain failure;
- invalid seed length consumes the claimed identity;
- failure after private seed persistence retains the failure
  evidence and prohibits retry;
- public artifacts exclude raw synthetic seed bytes;
- successful commitment equals SHA256 of the synthetic seed;
- public and private filesystem permissions are restrictive;
- symbolic-link and non-directory boundaries are rejected;
- unrelated historical and protected artifacts remain unchanged.

Fault injection must be restricted to temporary development
fixtures.

No scientific treatment, protected generation, or real C1
seed-generation entrypoint may be invoked.

### Confirmed persistence semantics

The one-shot identity is claimed before invoking the injected
synthetic seed factory.

Once an identity is claimed, failures and incomplete attempts
do not authorize another attempt with that same identity.

A FAILED disposition is authoritative for a handled failure even
when private seed material or a public commitment file is visible.

The `seed_persisted` field indicates successful completion of the
private seed persistence phase, including the requested
synchronization, not a universal assertion of filesystem presence.

In the tested private-seed directory-sync failure, the raw seed file
was visible but `seed_persisted` remained false because durable
publication was not confirmed.

Therefore, `seed_persisted=False` must never be interpreted as proof
that private seed bytes are absent from storage.

Post-claim failures retain the consumed identity even when a failure
disposition cannot be durably completed.

A STARTED or incomplete identity must not be rerolled.

### Temporary-file cleanup limitations

Handled interrupted writes clean up their temporary files in the
qualified synthetic failure scenarios.

Abrupt process termination, machine failure, or power loss may
interrupt cleanup. Residual private temporary files must be treated
as sensitive and must not authorize seed regeneration.

No automatic cleanup or retry process is qualified by this
development increment.

### Filesystem and authorization limitations

The implementation constrains development operations to a configured
temporary-directory boundary, rejects paths inside the repository,
and checks for symbolic-link components below the trusted temporary
root during preflight.

Those checks do not provide complete race-resistant filesystem
security. Concurrent path replacement, symlink substitution after
validation, directory ownership changes, and adversarial filesystem
manipulation are not qualified.

No descriptor-relative path traversal or fully race-resistant
authorization mechanism has been implemented.

The claim is exclusive within a selected development root; this does
not prove global one-shot uniqueness across arbitrary roots.

The seed factory is caller-supplied and is used with synthetic
development fixtures. The module does not independently enforce
cryptographic seed provenance or scientific authorization.

The development `public` directory is a logical evidence category;
its Unix permissions are intentionally restrictive rather than
world-readable.

The development implementation is not a protected seed-generation
entrypoint and must not be invoked as one.

### Crash durability boundary

The implementation uses file synchronization, directory
synchronization, exclusive publication, and disposition replacement.

The fault-injection tests exercise selected failures from these
operations, but they do not establish a universal crash-consistency
or durability guarantee across platforms and filesystems.

File visibility does not prove that directory persistence was
confirmed.

A post-publication synchronization error remains a failed attempt,
regardless of whether a file can subsequently be read.

Any future protected implementation requires a separately approved
storage and recovery contract, including the handling of uncertain
durability states.
