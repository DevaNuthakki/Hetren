# P09.4 Development-Only Environment and Protocol Feasibility Specification

## Status

**PRE-IMPLEMENTATION DEVELOPMENT SPECIFICATION — NO PROTECTED EXECUTION AUTHORITY**

This document translates the P09.4A1 architecture direction into a concrete
development-only environment and protocol specification.

It freezes what the development implementation must demonstrate before final
P09.4 cost calibration, protected-population design, numerical thresholds,
preregistration, or protected execution may occur.

This document is not the final P09.4 preregistration.

---

## Grounded starting point

The existing deterministic incident-triage environment already provides a
useful but insufficient foundation:

- two executable latent faults;
- a 10-event workflow trace;
- four tool-call/tool-result pairs;
- persistent state fingerprints;
- a real agent decision event;
- a report-building stage;
- deterministic execution;
- workflow-backed diagnostic evidence;
- and negative controls showing that the wrong intervention does not repair
  the unrelated existing fault.

The two existing development fault modes correspond naturally to:

- F1 tool-selection fault;
- F2 parameter-transformation fault.

P09.4 must add genuine F3, F4, and F5 mechanisms.

---

## Implementation isolation decision

P09.4 development must not rewrite the historical incident-triage environment
in place.

The existing files remain regression-preserved evidence for prior phases.

The preferred development implementation is a dedicated richer environment
and H1 diagnosis harness that may reuse stable contracts and implementation
ideas without silently changing prior demonstrations.

Candidate implementation paths are:

- `environments/agent/p09_4_multistep_incident.py`;
- `packages/engines/behavioral/p09_4_multistep_diagnosis.py`;
- `tests/integration/test_p09_4_multistep_diagnosis_development.py`.

These are development implementation targets, not protected-result paths.

---

## Development workflow state machine

The richer environment should implement a deterministic workflow with at least
the following logical phases:

### S0 — START

No operational data has been loaded.

### S1 — INCIDENTS_LOADED

The incident dataset has been loaded from the deterministic incident source.

### S2 — SERVICE_SCOPED

The workflow has selected incidents relevant to the target service.

### S3 — CONTEXT_LOADED

The workflow has loaded policy/context metadata needed for later decisions.

This phase creates an explicit state dependency needed for F4.

### S4 — STRATEGY_SELECTED

The agent has selected the severity/filter strategy and transformed its
parameters.

F1 and F2 primarily affect this decision boundary.

### S5 — INCIDENTS_FILTERED

The selected filtering action has been executed.

### S6 — INCIDENTS_ENRICHED

Additional environment/tool information required for downstream validation has
been retrieved.

This phase creates a distinct environment-interaction boundary needed for F5.

### S7 — NORMALIZED

The workflow has converted tool results into the canonical internal form used
by policy and validation.

### S8 — VALIDATED

The workflow has checked that the evidence satisfies the incident-report
requirements.

### S9 — REPORT_BUILT

The final triage report has been assembled.

### S10 — COMPLETE

The workflow has terminated and emitted the observable result.

The development implementation may use more internal states, but it must not
collapse away the state dependencies needed to distinguish F1-F5.

---

## Development trajectory requirement

The current historical incident path contains 10 trace events.

The richer development environment must be structurally more complex.

Before A2 development is considered feasible, every primary F1-F5 baseline
development run must contain:

- at least 13 trace events;
- at least five tool-call/tool-result interaction pairs;
- at least one agent decision;
- at least one additional state-sensitive decision or state-transition event;
- and a termination event.

This is a development feasibility requirement, not yet the final protected
trajectory threshold.

---

## Primary development fault mechanisms

Exactly one primary latent fault is injected per primary development case.

### F1 — Tool selection

Injection point: S4 STRATEGY_SELECTED.

Development mechanism:

Select a strict or otherwise incorrect severity/filter tool when the canonical
workflow requires the inclusive/correct implementation.

This reuses the existing executable tool-selection pattern.

### F2 — Parameter transformation

Injection point: S4 STRATEGY_SELECTED.

Development mechanism:

Select the correct tool but transform the canonical severity or policy
parameter incorrectly.

This reuses the existing executable threshold-transformation pattern.

### F3 — Sequencing / orchestration

Injection boundary: S5 through S8.

Development mechanism:

Execute a downstream normalization or validation action using an intermediate
result before a required prerequisite enrichment/state transition has been
completed.

The resulting workflow must actually consume the wrong stage state.

F3 must not be implemented as a hidden boolean that directly determines the
diagnostic verdict.

### F4 — State / context

Injection point: S3 CONTEXT_LOADED.

Development mechanism:

Load a deterministic stale or otherwise inappropriate context snapshot whose
value is later consumed by the strategy, policy, normalization, or validation
path.

The failure must arise because later workflow actions consume that state.

F4 must not be equivalent to simply changing the same threshold field used by
F2.

### F5 — Tool / environment interaction

Injection point: S6 INCIDENTS_ENRICHED.

Development mechanism:

Return a deterministic but contract-significant environment/tool response
variant such as incomplete enrichment, altered response semantics, or a
schema-compatible response whose meaning differs from the workflow's
assumption.

The workflow must fail because it interprets or depends on the real returned
environment evidence.

F5 must not be a relabeled F1 tool choice or F2 parameter error.

---

## Shared observable failure design

The development cases should intentionally share a coarse externally visible
failure signature wherever feasible.

For example, multiple F1-F5 mechanisms may produce the same incorrect final
incident-report membership or count while differing in the internal trace and
state transitions that caused it.

The purpose is to prevent diagnosis from being reducible to reading a unique
final-output label.

The exact protected failure-signature construction is not frozen here.

---

## Rival Fault Set

The primary development Rival Fault Set contains five hypotheses:

- `tool_selection_fault`;
- `parameter_transformation_fault`;
- `sequencing_orchestration_fault`;
- `state_context_fault`;
- `environment_interaction_fault`.

Development may initially use uniform priors solely to exercise mechanics.

Final protected priors, if non-uniform, must be justified and preregistered
before protected evaluation.

Treatment must never receive the evaluator's latent fault label.

---

## Candidate diagnostic probes

The development experiment catalogue should contain at least one executable
probe aimed at each major mechanism.

### P1 — Canonical tool probe

Conceptual intervention:

- `REPLACE_TOOL`;
- target: strategy/tool selection.

The executor runs the relevant isolated workflow with the canonical tool while
otherwise preserving the case.

### P2 — Canonical parameter probe

Conceptual intervention:

- `OVERRIDE_PARAMETER`;
- target: canonical parameter transformation.

The executor reruns the relevant isolated workflow with the canonical value.

### P3 — Canonical prerequisite/order replay

Conceptual intervention:

- `REPLAY`;
- target: orchestration prerequisite/order.

The executor recreates the same faulted case but executes the suspect stage
from the canonical prerequisite state/order.

### P4 — Fresh-context replay

Conceptual intervention:

- `REPLAY`;
- target: context/state refresh.

The executor recreates the same faulted case using canonical fresh context at
the S3 boundary.

### P5 — Environment-contract replay

Conceptual intervention:

- `REPLAY`;
- target: environment/tool response contract.

The executor recreates the same faulted case against the canonical deterministic
environment response at the S6 boundary.

Using `REPLAY` for P3-P5 is acceptable only if the intervention target and
executor behavior give each probe distinct auditable semantics.

A new InterventionKind must not be added merely for naming convenience.

If development shows that the existing intervention vocabulary cannot express
a required action without semantic distortion, implementation must stop for a
separate reviewed contract-change decision.

---

## Sequential-information requirement

P09.4 must remain meaningfully sequential.

With five competing hypotheses and binary PASS/FAIL observations, no single
ordinary diagnostic observation should encode the full hidden fault identity.

At least one observation branch for each development experiment must leave
more than one in-RFS hypothesis viable.

The development harness must demonstrate at least one valid case where a
diagnosis policy requires two or more observations before reaching a correct
specific diagnosis.

The final protected prediction matrix will be frozen only after development
mechanics are validated.

---

## Workflow-backed observation rule

A diagnostic Observation must be derived from the actual executed development
workflow.

The executor may use the selected experiment to choose which isolated
intervention to run.

It must not determine the observation by copying the experiment's
`predicted_verdicts`, reading the evaluator's hidden fault label and returning
the registered answer directly, or consulting a case-to-verdict lookup table.

The observation evidence hash must bind real execution evidence from the
diagnostic run.

A FAIL observation should preserve an auditable counterexample/evidence
reference where technically appropriate.

---

## Experiment-state isolation

Every diagnostic experiment must begin from the same reproducible baseline
case snapshot for that arm unless an experiment explicitly preregisters a
different state dependency.

An experiment must not permanently repair, corrupt, or mutate shared case state
for the next experiment.

The development harness must prove that experiment ordering does not alter the
underlying baseline bytes/state for later probes.

Planner posterior state may accumulate observations.

Environment state used to generate each diagnostic observation must remain
isolated and reproducible.

---

## C0-C3 development harness

The development implementation must support the same conceptual arms as P09.3:

- C0 — trace-only;
- C1 — seeded-random active selection;
- C2 — maximum raw expected information gain;
- C3 — HEAL information gain per declared cost.

The development harness must not change the meaning of an arm merely to improve
its result.

All arms receive the same initial observable case state, trace, hypotheses,
experiment catalogue, and declared budget.

C0 obtains no actively generated diagnostic evidence.

C1-C3 may differ only through their registered experiment-selection behavior.

---

## Development cost calibration instrumentation

Exact planner costs are intentionally not frozen in A2B.

Every development probe must report enough realized resource accounting to
permit later cost calibration without protected-result tuning.

Required development counters are:

- diagnostic experiment count;
- tool/environment interaction count;
- workflow event/step count;
- and declared cost units.

The initial calibration candidate should relate declared cost to expected
workflow/tool operations rather than arbitrary labels.

Final cost assignments are frozen only after development-only calibration.

---

## Development out-of-RFS safety control

A development-only case must contain a latent failure outside the five-member
Rival Fault Set.

The treatment does not receive an `out_of_rfs` label.

The evaluator retains that truth separately.

The safety requirement is:

**the treatment must not produce a confident specific F1-F5 diagnosis when the
executed evidence does not support one.**

For P09.4 development, the existing `INCONCLUSIVE` terminal state is the
preferred conservative representation.

A new `UNKNOWN` or `OUT_OF_RFS` DiagnosisStatus is not justified yet because
H1 requires an abstention/false-certainty check, not a new public taxonomy.

If the existing planner/lifecycle cannot reach `INCONCLUSIVE` for a valid
out-of-RFS evidence pattern without corrupting normal in-RFS semantics,
implementation must stop.

At that point a separate reviewed core-contract change is required before
continuing.

The implementation must not silently reinterpret `BUDGET_EXHAUSTED` as
`INCONCLUSIVE` or unknown.

---

## Development-only cases

The minimum development suite should contain at least:

- one executable F1 case;
- one executable F2 case;
- one executable F3 case;
- one executable F4 case;
- one executable F5 case;
- one out-of-RFS safety case;
- and at least one neutral/control case suitable for cost-policy sanity
  checking.

These development cases are inspectable and may be revised during development.

They must never later be relabeled as protected evidence.

---

## Development acceptance tests

P09.4 may advance from development implementation to calibration only if the
following acceptance conditions are satisfied.

### A — Legacy preservation

- all pre-P09.4 tests remain green;
- existing incident-triage behavior remains unchanged;
- existing P09.3 protected hashes remain unchanged.

### B — Real multi-step execution

- every F1-F5 baseline executes the richer workflow;
- each primary baseline has at least 13 trace events;
- at least five tool-call/tool-result pairs occur;
- state hashes change across meaningful workflow phases;
- and later actions consume outputs/state produced by earlier stages.

### C — Genuine heterogeneous faults

- F1 changes tool selection;
- F2 changes parameter transformation;
- F3 changes orchestration/prerequisite semantics;
- F4 changes state/context semantics;
- F5 changes environment-response semantics;
- and source/tests demonstrate that F3-F5 are not aliases of F1/F2.

### D — Baseline ambiguity

- multiple fault families share the same coarse visible failure signature;
- treatment cannot infer the latent family from an evaluator-only label;
- and the final-output value alone is insufficient to identify all five
  primary faults.

### E — Executed diagnostic evidence

- every selected diagnostic probe executes workflow behavior;
- observations bind actual execution evidence;
- the executor does not copy `predicted_verdicts`;
- and no case-to-verdict shortcut is present.

### F — Sequential diagnosis

- the prediction/evidence structure contains ambiguous observation branches;
- at least one development case requires two or more observations for correct
  specific diagnosis;
- and the planner/harness can execute the sequential lifecycle within budget.

### G — Isolation

- every diagnostic probe starts from the same case baseline snapshot;
- probe ordering does not mutate later experiment starting state;
- and repeated identical runs produce identical evidence hashes.

### H — Negative controls

- at least one wrong-target intervention remains failing for each primary fault
  family where a meaningful wrong-target control exists;
- a neutral/cost sanity case is executable;
- and out-of-RFS treatment does not manufacture a specific F1-F5 diagnosis.

### I — Resource accounting

- declared cost is recorded;
- actual diagnostic experiment count is recorded;
- actual tool/environment interaction count is recorded;
- and actual workflow-step count is recorded.

### J — Authority boundary

- development diagnosis creates no repair authority;
- no verification result is manufactured;
- no eligibility result is manufactured;
- no protected-result claim is manufactured;
- and H2-H5 remain outside the result surface.

---

## Development failure policy

A development design failure is informative.

Examples include:

- F3-F5 cannot be made behaviorally distinct without artificial shortcuts;
- the five-fault observation matrix collapses to trivial one-step lookup;
- the planner cannot handle the richer sequential evidence cleanly;
- out-of-RFS safety cannot be represented by `INCONCLUSIVE` without semantic
  distortion;
- intervention state contaminates later probes;
- or resource accounting cannot be defined consistently.

A failure of one of these conditions requires design revision before
preregistration.

It must not be hidden by generating protected data early.

---

## Values still intentionally unfrozen

A2B does not freeze:

- final protected template count;
- final protected case count;
- final protected F1-F5 distribution;
- exact protected priors;
- exact prediction matrix;
- exact planner cost table;
- exact diagnosis budget;
- exact C1 seed procedure;
- protected generation seed;
- protected assignment procedure;
- final numerical H1 support threshold;
- final false-specific tolerance;
- protected artifact paths;
- or protected execution identity.

Those values must be chosen only after development mechanics and calibration
are complete, then preregistered before protected generation.

---

## Claim boundary

Passing the A2 development acceptance tests would establish only that the
richer deterministic environment and protocol are technically feasible.

It would not establish that C3 is scientifically better than the baselines.

It would not establish realistic-agent effectiveness.

It would not establish model-backed robustness.

It would not establish multi-fault diagnosis.

It would not establish repair correctness, verification quality, production
reliability, external validity, or state-of-the-art performance.

Scientific comparison begins only after the protected P09.4 protocol is
preregistered and valid protected results are frozen.
